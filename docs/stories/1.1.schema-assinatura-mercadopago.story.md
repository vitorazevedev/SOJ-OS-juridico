## Story

**As a** administrador do sistema (equipe Ponderum),
**I want** que o banco de dados tenha as tabelas/colunas necessárias para rastrear assinaturas do Mercado Pago por organização, e que a RPC manual existente aceite um tier específico,
**so that** o restante do épico tenha uma base de dados sólida para se apoiar, e a equipe não perca a capacidade de suporte manual durante a transição.

## Dependencies

Nenhuma — esta é a primeira story do Epic 1 (checkout digital via Mercado Pago). As Stories 1.2-1.7 dependem desta (schema e RPC estendida precisam existir antes de qualquer Edge Function de pagamento ou UI ser construída).

## Estimation

**T-shirt size**: M — duas tabelas novas (schema simples, sem lógica de negócio), extensão de uma RPC existente preservando compatibilidade, sem endpoint HTTP nem UI nesta story.

## Acceptance Criteria

1. Nova tabela liga `organizations.id` a `subscription_id`/`customer_id` do Mercado Pago, com RLS restringindo cada organização a ver só a própria linha.
2. Nova tabela/coluna registra o `event_id`/`payment_id` de cada webhook já processado, usada como base de idempotência (consumida pela Story 1.3, não implementada aqui).
3. `organizations.plan_id` aceita os novos valores (`individual`, `escritorio`, `juridico`, `corporativo`), mantendo `starter` funcional para organizações existentes.
4. `staff_set_org_plan_status` é estendida para aceitar um parâmetro de tier, preservando compatibilidade com chamadas existentes (sem o novo parâmetro).
5. Todas as tabelas/colunas novas têm RLS habilitada e testada antes do merge.

## Dev Notes

**Contexto do PRD** [Source: docs/prd-mercadopago-checkout.md#technical-constraints-and-integration-requirements]:
Esta story é a base de todo o Epic 1 (checkout digital via Mercado Pago). Nenhuma Edge Function de pagamento é criada aqui — só o schema e a extensão da RPC manual.

**Mecanismo manual já existente** [Source: docs/prd-mercadopago-checkout.md#current-project-state]:
O upgrade/renovação manual hoje já é formalizado via duas RPCs `SECURITY DEFINER` em `supabase/migrations/20260728000000_billing_receipts.sql`:
- `staff_set_org_plan_status(p_org_id uuid, p_status text)` — só aceita `p_status in ('trial', 'active')`, checa `is_ponderum_staff`, atualiza `organizations.plan_status`/`plan_renews_at`, e insere uma linha em `billing_receipts` no primeiro pagamento.
- `staff_renew_org_subscription(p_org_id uuid)` — renova por mais 30 dias, insere linha de renovação em `billing_receipts`.

Esta story estende SÓ a primeira (`staff_set_org_plan_status`) para aceitar tier — `staff_renew_org_subscription` não precisa mudar nesta story (renovação automática real é tratada pela Story 1.3, webhook).

**Padrão de RLS já estabelecido** (verificado nesta sessão via `pg_policies`):
```sql
-- contracts_select
(org_id = get_org_id())
-- analyses_select (contract_analyses)
(contract_id IN (SELECT contracts.id FROM contracts WHERE contracts.org_id = get_org_id()))
```
As tabelas novas desta story devem seguir o padrão mais simples (`org_id = get_org_id()` direto), já que ambas terão `org_id` como coluna própria.

**Cuidado com `security_invoker`** [Source: trabalho desta mesma sessão, commit `9668713`]: Se qualquer view nova for criada sobre as tabelas desta story, ela precisa nascer com `security_invoker = true` (ou equivalente) — uma view sem isso ignora RLS e rodou com o privilégio de quem a criou. Esse exato bug foi encontrado e corrigido em `contract_analyses_gated` nesta sessão (ver `supabase/migrations/20260901000000_fix_gated_view_security_invoker.sql`). Não é esperado que esta story precise de view nova, mas o alerta vale se o `@data-engineer` decidir criar uma.

**Pontos não verificados, a confirmar durante a implementação**:
- Se existe `CHECK constraint` em `organizations.plan_id` (ver Task 3) — não foi verificado nesta sessão.
- Nome exato das duas tabelas novas — deliberadamente não travado no PRD nem aqui; decisão do `@data-engineer`, seguindo a convenção `snake_case` já usada no projeto (ex: `clause_risks`, `billing_receipts`).

### Completion Notes List

- Tasks 1-4 implementadas na migration `supabase/migrations/20261013000000_mercadopago_subscriptions_schema.sql`, aplicada em produção depois que o usuário reautenticou a CLI (acesso caiu e voltou duas vezes nesta sessão — mesma instabilidade intermitente já vista antes, não um problema do código).
- **Bug real encontrado durante a verificação de IV3 (não durante a escrita, durante o teste)**: `CREATE OR REPLACE FUNCTION public.staff_set_org_plan_status(p_org_id uuid, p_status text, p_plan_id text DEFAULT NULL)` não substituiu a função original de 2 argumentos — Postgres trata assinaturas com parâmetros diferentes como funções distintas (overload), não como a mesma função atualizada. Resultado: ficaram DUAS versões coexistindo, e a de 2 argumentos manteve a lógica antiga (recibo sempre fixo em "Starter"/R$490), não a correção do tier. Corrigido com uma segunda migration (`20261013010000_fix_duplicate_staff_set_org_plan_status.sql`, `DROP FUNCTION` da versão de 2 argumentos), aplicada e verificada via `pg_proc` — restou só uma função, com `p_plan_id` opcional, call-compatível com 2 ou 3 argumentos.
- Tipos TypeScript regenerados (`supabase gen types typescript --linked`) e `npm run typecheck` limpo após a mudança de schema.
- **Achado durante a implementação (fora do escopo literal da Task 4, mas necessário para implementá-la corretamente)**: `staff_set_org_plan_status` gerava o recibo em `billing_receipts` com valor e descrição hardcoded (`49000`, `"Primeiro pagamento — Plano Starter"`), independente de qual plano estava sendo ativado. Isso ficaria incorreto ao estender a função para aceitar qualquer um dos 4 tiers novos — um recibo de "Plano Jurídico" (R$899) sairia registrado como R$490/Starter. Corrigido calculando `amount_cents`/`description` a partir do tier efetivo. Não é scope creep: é a implementação correta da AC4 ("estender para aceitar um tier específico") — aceitar o parâmetro sem corrigir o recibo deixaria a funcionalidade quebrada pela metade.
- Task 3 não pôde ser verificada contra o schema real (ver Debug Log). A migration foi escrita de forma defensiva (bloco `DO $$` que localiza e remove dinamicamente qualquer `CHECK constraint` existente em `plan_id`, sem precisar saber o nome dela de antemão) — deve funcionar corretamente em qualquer um dos dois cenários (com ou sem constraint pré-existente), mas recomendo rodar em ambiente de teste antes de aplicar em produção, já que esse trecho específico não foi exercitado contra o banco real nesta sessão.
- Nenhum arquivo TypeScript/frontend tocado nesta story — é puramente schema. `npm run typecheck`/`npm run lint` não se aplicam a este conjunto de mudanças (só SQL).
- Review do CodeRabbit (pré-commit) não executado nesta sessão — ferramenta roda via WSL, não disponível neste ambiente. Sinalizado como pendente, não bloqueador, mas deve ser considerado antes do `@devops` empurrar para o repositório remoto.

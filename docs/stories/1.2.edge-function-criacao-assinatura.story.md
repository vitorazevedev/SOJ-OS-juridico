## Definition of Done desta story (nota do PO)

**"Done" aqui significa "código completo, estruturalmente correto, e tudo que é testável sem credencial foi verificado de verdade" — NÃO significa "o checkout com o Mercado Pago está funcionando de ponta a ponta".** Isso é intencional (diretriz do PO: "deixar tudo pronto para apenas conectar"), mas precisa ficar registrado explicitamente para não virar uma suposição errada mais adiante — ninguém deve ler "Story 1.2: Done" e concluir que dá pra assinar um plano de verdade hoje. A conexão real com o Mercado Pago (confirmar `status` correto, formato da resposta, testar contra sandbox) é trabalho pendente, não desta story — fica registrado como follow-up a ser retomado quando a credencial existir, sem precisar reabrir ou reescrever esta story.

## Dependencies

Depende da Story 1.1 (Done) — usa diretamente `organization_mercadopago_subscriptions` (lock contra duplicata via `unique(org_id)`) e os novos valores de `organizations.plan_id`.

## Restrição confirmada com o PO (2026-10-18)

O PO ainda **não tem conta/credenciais do Mercado Pago** (nem sandbox). Diretriz explícita: *"deixar tudo pronto para apenas conectar com o Mercado Pago e ajustar os valores conforme os sócios definirem"*. Isso muda o que "pronto" significa nesta story:

- A function fica **code-complete e estruturalmente correta**, mas a chamada real ao endpoint `/preapproval` do Mercado Pago **não pode ser testada contra a API real nesta story** — fica pronta no código, não verificada ponta a ponta. Isso não é um débito escondido: é uma dependência externa explícita (credencial inexistente), documentada aqui e repetida no AC5.
- Tudo que NÃO depende da API externa (autorização, lock de duplicata, ausência de segredo configurado) **deve** ser testado de verdade — não tem desculpa pra pular isso.
- Os valores dos 4 planos pagos (Individual R$199, Escritório R$499, Jurídico R$899, Corporativo R$1.749 — vindos de peças de campanha dos sócios, **sujeitos a mudar**) precisam viver num único lugar fácil de editar, não espalhados pela lógica da function.

## Estimation

**T-shirt size**: M — uma Edge Function nova, lock reaproveitando schema já pronto, sem UI. A parte estruturalmente mais delicada (chamada HTTP ao Mercado Pago) é escrita mas não testável agora.

## Story

**As a** usuário admin de uma organização,
**I want** iniciar uma assinatura de um dos 4 planos pagos a partir do app,
**so that** eu consiga assinar a Ponderum sem precisar falar com o time de vendas.

## Acceptance Criteria

1. Nova Edge Function monta a chamada para criar uma `preapproval` no Mercado Pago para o plano escolhido, autenticada via JWT do usuário. **Chamada real não testável nesta story** — sem credencial (ver seção "Restrição confirmada com o PO").
2. A function valida que o usuário é admin da organização antes de criar a assinatura (FR14) — testável sem Mercado Pago.
3. A function impede criar uma segunda assinatura ativa se a organização já tiver uma (FR13), usando o `unique(org_id)` já existente em `organization_mercadopago_subscriptions` (Story 1.1) — testável sem Mercado Pago.
4. A function retorna a URL de checkout hospedado do Mercado Pago (`init_point`) para o frontend redirecionar o usuário — a montagem da resposta é testável; o valor real da URL só quando houver credencial.
5. Se `MERCADOPAGO_ACCESS_TOKEN` não estiver configurado, a function falha com um erro claro e específico (nunca um erro genérico/obscuro) — testável sem Mercado Pago, é literalmente testar a ausência do segredo.
6. Os valores/limites dos 4 planos pagos vivem num único arquivo de configuração, não espalhados pela lógica da function — editar um preço não deve exigir entender o resto do código.

## Integration Verification

- IV1: Usuários sem `role='admin'` na organização recebem erro de autorização, sem conseguir criar assinatura.
- IV2: Tentar criar uma segunda assinatura para a mesma organização falha de forma clara, sem duplicar nada no banco (reaproveita o `unique(org_id)` da Story 1.1 — não precisa de lock adicional em código, só tratar o erro de violação de forma amigável).
- IV3: Nenhuma mudança no comportamento de upload/análise de contrato existente (`parse-contract`, `analyze-contract` não tocados nesta story).

### Achado 1 (sério — recomendo resolver antes de considerar esta funcionalidade pronta pra uso real, mesmo que não bloqueie "Done" desta story específica)

**O placeholder do lock pode ficar órfão para sempre se a function cair entre o INSERT (linha 97) e o `fetch`/`delete` de reversão (linhas 109-161) — exatamente a mesma classe de bug do incidente real da Matrix desta sessão (lock sem mecanismo de staleness/reclaim).**

Se a invocação for interrompida depois de reservar o vínculo (timeout, cold start, falha de rede chegando no Mercado Pago, restart de deploy) mas antes de qualquer um dos `delete`/`update` rodar, a linha em `organization_mercadopago_subscriptions` fica presa com um `mp_subscription_id` fake (`pending_...`) pra sempre. Como a tabela tem `unique(org_id)`, a organização **nunca mais consegue tentar assinar de novo** através desta function — toda tentativa futura esbarra no código `23505` e devolve "Esta organização já tem uma assinatura ativa", mesmo sem assinatura nenhuma de verdade. Só um humano mexendo direto no banco destrava — exatamente o cenário que motivou toda a arquitetura de autorrecuperação construída mais cedo nesta sessão (progresso real, retomada automática, watchdog por cron) para a análise de contratos.

A Story 1.5 (reconciliação periódica) eventualmente cobre isso, mas ainda não existe, e mesmo quando existir, o desenho dela (PRD) é para reconciliar contra o Mercado Pago, não especificamente para destravar um placeholder que nunca chegou a existir do lado do Mercado Pago. **Recomendação**: antes de ligar esta function pra usuários reais (ou seja, antes da Story 1.4 — UI — ir ao ar), adicionar uma checagem de staleness no INSERT do lock (mesmo padrão já usado em `analyze-contract`/`parse-contract`: `WHERE ... AND (created_at IS NULL OR created_at < staleThreshold)` em vez de um `unique` simples), permitindo reclamar um placeholder abandonado há mais de alguns minutos.

### Achado 2 (menor — vale corrigir, não bloqueia)

**O erro do `.update()` final (linha 146-150, que troca o placeholder pelo id real da assinatura) é descartado silenciosamente** — não há `const { error } = await ...` nem tratamento. Se essa chamada falhar por qualquer motivo transitório, uma assinatura real passa a existir no Mercado Pago, mas a linha em `organization_mercadopago_subscriptions` continua com o `mp_subscription_id` placeholder (fake), nunca vinculada à real — o usuário pagou, mas o sistema não sabe. **Recomendação**: capturar e logar esse erro (no mínimo), já que é uma linha de código, sem a complexidade do Achado 1.
